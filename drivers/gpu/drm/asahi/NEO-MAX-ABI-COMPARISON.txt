Neo and M4 Max firmware topology and lifecycle comparison
2026-10-25

Conclusion

The pointer topology and fundamental lifetime rules are very similar. The
known working paths support one queue-generation and ownership implementation,
with ABI-specific submission handling. They do not justify independent CPU
schedulers or independent resource-lifetime implementations.

Reference: original Neo driver at neo-known-good-2026-10-21,
a6883c3c6e5aa42548543a5a7b82bb6e375d6922. Forty-six original source files were
compared with Max's source-built protocol and working native captures, rather
than relying only on the newer shared structs.

Detailed read-only evidence is in the adjacent bootloader checkout:
build/m4max-gpu/g16c-g17p-abi-comparison-20261025/
  original-neo-provenance.json
  original-neo/
  topology-and-lifecycle.json
  render-role-map.json

Common pointer graph and lifetime rules

* Firmware queues point to a pointer block, item ring, job list, and queue
  context. Outer channel messages identify the queue and published work head.
* Persistent execution contexts have low/high aliases of retained context
  records. Records reference descriptors, queues, predecessor milestones,
  and register arrays.
* Compute descriptors reference scheduler/credit records, command streams,
  save/operand state, completion destinations, timestamps, and pool support.
* Render has corresponding work-state, scene, shared parameter/index-manager,
  and empty-object roles. Tiling and fragment retain shared resources through
  partial continuation and completion.
* Dependencies name predecessor queue milestones. Producer identities remain
  valid while consumers can still reference them.
* Queue consumption, GPU completion, report processing, and CPU visibility are
  separate conditions. Consumption alone does not authorize storage reuse.
* Reconfiguration retires affected work, performs context cleanup, and then
  re-registers or reuses retained storage. Logical closure does not immediately
  free every object reachable by firmware.

Render role correspondence

Original Neo                      M4 Max
Pool A selected work-state record Event-control object
Pool B selected record            Scene
Shared parameter/index object     Parameter manager
Zero object                       Empty scene

These are corresponding roles, not proof of identical mutation semantics for
every firmware-written byte. The parameter-manager graph contains the same
broad classes of page/index lists, block IDs, shared control, and counter state.

Three observed firmware protocol differences

1. Submission entry
   Original Neo independent compute publishes descriptor, optional context
   setup, and event on registration; later work publishes descriptor and event.
   The qualified Max path publishes a Work15 wrapper and marker. Work15 selects
   a persistent context-array record, which references the descriptor. The
   wrapper and context-record concepts already exist in Neo; their use within
   the submission sequence differs. The observed Max wrapped path does not
   prove that every alternate direct-descriptor path is impossible.

2. Context binding
   Max's qualified path explicitly installs/resumes execution-context bindings
   through SGX transactions. Neo ordinary independent-compute publication has
   no equivalent per-publication host transaction. This is an ABI-specific
   binding operation, not a second scheduling/lifetime model.

3. Firmware peers, reports, and control protocols
   Neo has two firmware instances; the qualified Max boot uses one. Completion
   reports, pool registration metadata, and some control sequencing differ.
   Growth replies retain Neo's first five words; Max additionally carries an
   observed opaque sixth word. See the context-isolated test below.
   Ownership still requires retaining the request owner, validating the reply,
   and establishing retirement before reuse. Wire identity/encoding and the
   observed protocol sequence must remain capture-backed.

Implementation differences that are not established ABI requirements

* Neo bundles an executable root/ASID, private operand storage, and firmware
  queue within a retained compute generation. The Max port instead separates
  VM Owner from Queue and largely fixes a pool within Owner. These are driver
  ownership policies, not evidence that the ABIs require different schedulers.
* The Max native capture proves that two queues share one operand pool. The
  original queue later uses a different pool while its ASID, actual root
  pointers, firmware queue, queue context, and context-array identity remain
  unchanged. Pool, VM, and queue lifetime are independent identities.
* Neo already implements off-lock preparation, exact seed revalidation,
  generation selection, and producer dependency retention. Max bypasses or
  reimplements portions of those paths.
* Neo preserves firmware-written portions of reused context records. Max
  currently writes complete records. This requires review and evidence, not
  an assumption that Max requires a different lifecycle. It is not an identified
  cause of the existing pre-wrap handoff timeout.
* Original Neo conservatively retains published GEM backing until Session
  teardown. Max adds more explicit per-owner retirement/reuse. This is added
  implementation complexity, not a demonstrated firmware topology difference.
* Max's global drain restrictions are conservative port restrictions, not an
  established firmware-wide serialization requirement.

Implication and limitation

Use Neo's generation selection, preparation/commit, dependency retention,
retirement, and reconfiguration machinery. Keep versioned fields and constant
templates. Keep the three protocol differences above explicit underneath that
common machinery. Do not infer lifetime ownership from numerical address
placement or equate one pool with one VM or queue.

This comparison does not identify the cause of the current short-incoming-job
handoff timeout. It provides no evidence for a fundamental firmware limitation
that requires independent Max scheduler/admission/lifetime managers.

Operator direction, 2026-10-25

Snapshot the existing Max integration before removing its divergent machinery.
Retain separate behavioral paths only where the three protocol differences
above justify them. Struct versioning and templating remain the means of
representing differing fields, constants, and wire geometry.
